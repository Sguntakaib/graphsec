PHASE 2: NODE-SPECIFIC THREAT LOGIC (Weeks 3-4)
================================================================================

OBJECTIVE: Implement context-aware threat application for each node category

2.1 APPLICATION LAYER THREAT LOGIC
----------------------------------

WebApp Threats:
- Spoofing: Only if has authentication (not anonymous access)
- Tampering: Only if processes user input (forms, APIs, uploads)  
- Repudiation: Only if requires audit trails (business transactions, compliance)
- Information Disclosure: Only if handles sensitive data (not public content)
- Denial of Service: Only if lacks infrastructure protection (no CDN/WAF)
- Elevation of Privilege: Only if has authorization model (user roles)

API Threats:
- Context-aware based on:
  * API type (REST, GraphQL, SOAP) 
  * Authentication method (public, API key, OAuth)
  * Data sensitivity (public APIs vs internal APIs)
  * Rate limiting and protection infrastructure

Lambda Threats:  
- Context-aware based on:
  * Trigger type (HTTP, Event-driven, Scheduled)
  * Permission model (execution role, resource access)
  * Data processing (stateless vs stateful operations)

2.2 DATA LAYER THREAT LOGIC
---------------------------

Database Threats:
- Spoofing: Only if lacks strong authentication (not certificate-based)
- Tampering: Always relevant (data integrity critical)
- Repudiation: Based on audit/compliance requirements  
- Information Disclosure: Based on data sensitivity classification
- Denial of Service: Based on availability requirements and protection
- Elevation of Privilege: Based on access control model complexity

S3 Threats:
- Context-aware based on:
  * Bucket access (public, authenticated, private)
  * Data classification (public content vs sensitive data)
  * Versioning and backup requirements
  * Cross-account access patterns

RDS Threats:
- Enhanced database logic with:
  * Multi-AZ deployment context
  * Read replica security considerations  
  * VPC and network isolation context

2.3 INFRASTRUCTURE LAYER THREAT LOGIC
-------------------------------------

EC2 Threats:
- Context-aware based on:
  * Instance role (web server, database, compute)
  * Network placement (public subnet, private subnet, isolated)
  * Administrative access requirements
  * Patch management and hardening status

Kubernetes Threats:
- Context-aware based on:
  * Cluster exposure (public LoadBalancer, internal services)
  * Workload types (web applications, batch jobs, data processing)
  * RBAC complexity and service account usage
  * Network policies and segmentation

VPC/NetworkACL/SecurityGroups:
- Context-aware based on:
  * Network exposure patterns
  * Trust boundaries and segmentation
  * Inter-VPC communication requirements
  * Ingress/egress rule complexity

2.4 SECURITY SERVICES THREAT LOGIC
----------------------------------

WAF Threats:
- Effectiveness based on protected resources
- Configuration completeness (rules, monitoring)
- Bypass potential based on architecture

IAM Threats:  
- Policy complexity and over-permissive access
- Cross-account trust relationships
- Service account and role usage patterns

KMS/SecretsManager:
- Key usage patterns and access controls
- Encryption scope and key rotation
- Secret access patterns and lifecycle management

2.5 INTEGRATION & DELIVERY THREAT LOGIC
---------------------------------------

CICD Threats:
- Pipeline security based on:
  * Code repository access controls
  * Build environment security  
  * Deployment target sensitivity
  * Artifact signing and verification

APIGateway Threats:
- Gateway configuration and protection capabilities
- Backend service security dependency
- Rate limiting and DDoS protection effectiveness

CDN Threats:
- Content security and cache poisoning risks
- Origin server protection effectiveness
- Geographic distribution security implications

PHASE 4: CROSS-NODE THREAT CORRELATION (Weeks 7-8)  
================================================================================

OBJECTIVE: Implement intelligent threat correlation across node relationships

4.1 TRUST BOUNDARY ANALYSIS
---------------------------

Identify and analyze trust boundaries:
- Network boundaries (public/private subnets, VPCs)
- Authentication boundaries (authenticated vs anonymous zones)
- Authorization boundaries (different permission levels)
- Data classification boundaries (public vs confidential data zones)

4.2 SHARED CONTROL ANALYSIS
---------------------------

Analyze how security controls protect multiple nodes:
- WAF protecting multiple web applications
- IAM policies affecting multiple AWS services  
- VPC security groups protecting multiple instances
- KMS keys protecting multiple data stores

Impact on threat calculation:
- Reduce individual node threat scores if protected by shared controls
- Create aggregate threats for shared control failures
- Identify single points of failure in security architecture

4.3 DATA FLOW SECURITY ANALYSIS
-------------------------------

Trace sensitive data flows and apply appropriate protections:
- Identify all nodes handling confidential data
- Ensure consistent encryption across data flow path
- Verify access controls at each data processing point
- Check for data leakage points (logs, error messages, backups)

4.4 ATTACK PATH ANALYSIS
------------------------

Model potential attack paths across multiple nodes:
- Initial access points (public-facing applications)
- Lateral movement paths (internal network access)
- Privilege escalation opportunities (IAM, service accounts)  
- Data exfiltration endpoints (databases, storage, APIs)

5.2 DECLARATIVE THREAT RULES
----------------------------

YAML-based threat rule definitions:

```yaml
# Example: webapp_threats.yaml
threats:
  - id: "webapp_input_validation_tampering"
    stride_category: "Tampering"
    title: "Input Validation Weakness"
    conditions:
      - question: "webapp_input_validation"
        values: ["No validation", "Client-side only", "Basic validation"]
      - context: "processes_user_input"
        value: true
    risk_base: 6.0
    mitigations:
      - condition: "has_database_connection"
        recommendation: "Implement parameterized queries and comprehensive server-side validation"
      - condition: "has_api_endpoints"  
        recommendation: "Implement schema validation and input sanitization"
      - default: "Add comprehensive server-side input validation"
```

5.3 CONTEXT CONDITION ENGINE
----------------------------

```python
class ContextConditionEngine:
    def evaluate_condition(self, condition: str, context: NodeContext) -> bool:
        """Evaluate complex contextual conditions"""
        
    def processes_user_input(self, context: NodeContext) -> bool:
        """Check if node processes user input based on multiple factors"""
        return (context.has_forms or context.has_api_endpoints or 
                context.has_file_uploads or context.database_connection)
                
    def handles_sensitive_data(self, context: NodeContext) -> bool:
        """Check if node handles sensitive data"""
        return context.data_sensitivity in ["Confidential", "Highly Confidential", "Regulated"]
```

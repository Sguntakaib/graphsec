Security Modeling Platform – Core Improvements Blueprint

Version: July 2025
Author: Main Agent

Executive Summary
This document consolidates current-state findings and proposes targeted improvements to strengthen the core questionnaire-to-vulnerability analysis pipeline across WebApp, API, Database, Backup, and Monitoring nodes. The main goals are: (1) unlock the enhanced conditional questionnaires so rules can reason more deeply about protocol/engine-specific risks, (2) make completeness checks accurate and consistent, (3) integrate Backup and Monitoring analysis into the main vulnerability surface, (4) correct front-end answer mapping to back-end rules, and (5) increase transparency, predictability, and maintainability of the system.

Top Priorities at a Glance
1) Enable conditional questionnaires (API/Database) in the UI so enhanced rules can trigger (GraphQL, gRPC, SOAP, MongoDB, PostgreSQL, etc.)
2) Fix completeness checks to always use comprehensive YAML endpoints for WebApp/API/DB/Backup/Monitoring
3) Stop injecting default insecure values client-side; rely on real answers and Unknown handling in rules
4) Align front-end mapping keys to rule keys (e.g., api_cors_configuration)
5) Integrate Backup analysis into the canvas vulnerability flow (and decide Monitoring strategy)

Current Architecture Overview (What works today)
- Questionnaires (YAML-based): WebApp, API, Database, Backup, Monitoring are delivered via /api/questionnaires/{NodeSubtype}?level=basic with options and option_descriptions (tooltips). These are great for a comprehensive baseline.
- Conditional Questionnaire Engine (code complete, not yet used by UI): Supports API types (REST/GraphQL/gRPC/SOAP/WebSocket) and DB engines (MySQL/PostgreSQL/MongoDB/Redis/Elasticsearch) with additional conditional questions. Endpoints: /api/questionnaires/{node_subtype}/conditional and /enhanced.
- Vulnerability Engine: Combines legacy rules (OR logic) and enhanced rules (AND logic) to generate VulnerabilityNode(s) with OWASP category + severity + MITRE techniques.
- Analyzer flow: UI sends questionnaire responses → backend preprocesses/derives a few indicators → rules evaluate → vulnerabilities created → frontend displays orbiting vulnerability nodes and filterable panels.

Key Gaps Identified
G1. Enhanced conditional rules are dormant: UI does not query conditional endpoints; therefore rules depending on api_type, database_type, and protocol/engine-specific fields (e.g., graphql_introspection, postgresql_row_level_security) rarely trigger.
G2. Completeness checks inconsistent: App uses YAML endpoint only for WebApp; for other types it queries legacy intelligent-nodes prompts count. This can misjudge completeness and block auto-analysis.
G3. Client-side default insecure injections: The UI mapping function sometimes inserts ‘No encryption’ or ‘HTTP only’ when users haven’t answered. This can create false positives and erode trust in results.
G4. Field name mismatches: Example: UI sets api_cors_policy while rules expect api_cors_configuration, preventing CORS misconfiguration rules from triggering.
G5. Backup analysis is off-path: We implemented /api/vulnerabilities/analyze/backup-security but the UI does not call it. The main engine has no Backup rules, so Backup nodes end up with 0 vulnerabilities even when risky answers exist.
G6. Monitoring node strategy is unclear: Monitoring is modeled as a control but there are no direct vulnerability rules for Monitoring nodes. Users may expect findings under Monitoring; today, logging/monitoring failures are flagged under WebApp/API answers.
G7. Category enums vs. rules: VulnerabilityCategory includes backup/monitoring-related categories (e.g., DATA_LOSS_RISK) but rules don&#39;t emit these, so categories are underutilized.
G8. Persistency & Traceability: Vulnerability analysis is cached in memory; it isn&#39;t persisted with diagrams. Re-opening a diagram may require re-analysis and loses audit trace if the service restarts.

Detailed Improvements (with rationale and implementation notes)

P1) Turn on conditional questionnaires for API and Database (High)
- Rationale: Unlocks the power of enhanced rules by collecting the required fields for protocol/engine-specific vulnerabilities (GraphQL injection/Introspection, gRPC streaming security, SOAP XML injection, PostgreSQL RLS, MongoDB auth/RBAC, etc.).
- Frontend changes:
  - When nodeSubtype in [API, Database], call GET /api/questionnaires/{node_subtype}/conditional?level=basic&amp;responses={...} (seed with current partial answers if any), instead of only the comprehensive YAML endpoint.
  - After each answer that is a conditional trigger (api_type, database_type, api_web_interface_exposure), call POST /api/questionnaires/{node_subtype}/conditional-trigger with {question_id, response} and append the returned questions into the current flow.
  - Keep option_descriptions in the UI for parity with YAML.
- Backend: Already implemented; no server changes required, only integration from the frontend.
- Expected outcome: Enhanced vulnerabilities will trigger meaningfully (e.g., GraphQL Injection, gRPC streaming insecurity, PostgreSQL RLS gaps, Mongo authorization issues).

P2) Fix completeness checks to use comprehensive YAML everywhere (High)
- Rationale: Prevent false &quot;incomplete&quot; states and ensure auto-analysis and bulk analysis behave deterministically.
- Frontend:
  - For WebApp/API/Database/Backup/Monitoring, fetch /api/questionnaires/{NodeSubtype}?level=basic and compute total_questions based on returned prompts.
  - Compare against the node&#39;s questionnaireResponses to decide if all required prompts are answered (Unknown counts as unanswered for completeness, or follow backend validation guidance).
- Backend: No changes required.

P3) Remove default-insecure client-side injections (High)
- Rationale: Avoid false positives; reflect actual user posture. Legacy rules already handle &quot;Unknown&quot; when we want cautious findings.
- Frontend:
  - In mapQuestionnaireResponsesToVulnRules(), do not auto-set webapp_data_encryption = &#39;No encryption&#39; or webapp_https_enforcement = &#39;HTTP only&#39; or other &quot;defaults&quot; unless the user explicitly chose them.
  - Keep boolean and list normalization minimal; let backend preprocessing convert booleans to Yes/No.
- Backend: No change required; it already normalizes and can handle Unknown in many rules.

P4) Fix mapping keys and value normalization (High)
- Rationale: Ensure rules match the UI payload and vice-versa.
- Concrete mapping fixes:
  - map api_cors_configuration (not api_cors_policy) to align with enhanced_vulnerability_rules.py
  - Ensure all YAML prompt IDs are sent as-is (e.g., api_input_validation, api_https_enforcement, webapp_input_validation, database_encryption_at_rest)
  - Avoid renaming fields to new keys if a rule already expects a specific one; prefer consistent names platform-wide.
- Add a unit test in frontend for mapQuestionnaireResponsesToVulnRules() to validate key/values coverage for common cases.

P5) Integrate Backup analysis into the main flow (High)
- Option A (faster): When analyzing a node of subtype Backup, call POST /api/vulnerabilities/analyze/backup-security with a security_config derived from backup.yaml answers. Merge those results into the existing vulnerability list and render on canvas.
- Option B (structurally cleaner): Convert backup-security checks into VulnerabilityRule(s) within the main engine (node_types=[&#39;Backup&#39;]), mapping backup_strategy, backup_encryption, backup_retention, backup_testing, backup_access_control, etc. This makes Backup behave like other node types.
- Recommendation: Start with Option A for speed, plan B for consolidation in Phase 2.

P6) Clarify Monitoring strategy (Medium)
- Option A (documented control): Keep Monitoring as a control without direct vulnerabilities. Add UI text in NodeInfoPanel: &quot;Monitoring nodes represent controls. Logging/monitoring failures are identified in WebApp/API nodes based on their answers.&quot;
- Option B (minimal rules): Add a handful of VulnerabilityRule(s) for Monitoring suboptimal states (e.g., No alerting, No retention, Shared access), mapped to OWASP A09 or Security Monitoring Failure categories.
- Recommendation: Implement Option A immediately; Option B in Phase 2 if users expect explicit monitoring risks visualized per node.

P7) Expand rule coverage to match available enums and questionnaires (Medium)
- Add VulnerabilityRule(s) for: Backup (if not doing Option B above), Monitoring (if chosen), and fill gaps where enums like DATA_LOSS_RISK/SECURITY_MONITORING_FAILURE are currently unused.
- Ensure OWASP and MITRE mapping stay realistic; keep severity/risk balanced across categories.

P8) Persistence and auditability for vulnerability analyses (Medium)
- Rationale: Keep analysis results with the diagram for reproducibility and offline review.
- Backend:
  - Extend diagram model to store last_vulnerability_analysis per node (summary + node list). Include timestamp and engine version.
  - Add GET/POST endpoints for saving/loading analysis per node and on bulk.
- Frontend:
  - On analyze, update diagram via PUT /api/diagrams/{id} with vulnerability data. On load, if persisted data exists, render from DB and offer &quot;Re-analyze&quot; button.

P9) UX improvements for transparency (Medium)
- Vulnerability detail panel already shows triggered_by_rule, user_selections, missing_controls, trigger_context. Add linked question text so users see exactly which question triggered which rule.
- For control-type nodes (Monitoring), display an info banner explaining how findings for that domain are surfaced.
- For incomplete questionnaires, show &quot;X of Y answered&quot; with direct link to outstanding questions.

P10) Testing and validation plan (High)
- Backend: Add tests for /questionnaires/{node_subtype}/conditional and /conditional-trigger flows (API &amp; DB). Validate enhanced rules on:
  - API: GraphQL injection, CORS misconfiguration, gRPC stream security, SOAP XML injection.
  - DB: PostgreSQL RLS disabled, MongoDB NoSQL injection/authorization issues.
  - Backup: backup-security endpoint end-to-end (encryption/access/testing/retention).
- Frontend: Add unit tests for mapping function and completeness function; E2E to exercise dependencies (WebApp → Database → Backup + Monitoring) and conditional sub-flows (API GraphQL path).

P11) Performance and caching (Low)
- Current in-memory cache TTL is 5 minutes. Add cache invalidation when questionnaire responses change and allow a &quot;force re-analyze&quot; client option.
- For bulk analyses, throttle UI to avoid spamming backend when users repeatedly click analyze.

P12) Documentation &amp; maintainability (Medium)
- Generate a &quot;Rule-to-Question&quot; mapping view:
  - Backend endpoint to enumerate rules along with required fields and provide example triggering selections. Helps authors keep YAML in sync with rules.
- Keep a living doc listing questionnaire prompt IDs and their intended mappings to rule keys, updated automatically from YAML and rule introspection if possible.

API Contract Changes (if we implement options above)
- No breaking backend changes required for P1–P4; they are frontend-only integrations/corrections.
- P5 Option A: UI calls existing POST /api/vulnerabilities/analyze/backup-security and merges response. Later (Option B), rules would be added; no contract change.
- P8 Persistence: New endpoints (proposed):
  - POST /api/diagrams/{id}/nodes/{node_id}/vulnerabilities { analysis }
  - GET /api/diagrams/{id}/nodes/{node_id}/vulnerabilities → returns last saved analysis

Rollout Plan
Phase 1 (1–2 days)
- Implement P1–P4: conditional questionnaire UI integration for API/DB; fix completeness checks; remove insecure defaults; correct mapping keys; smoke test with GraphQL and PostgreSQL paths.
- Quick add: NodeInfoPanel Monitoring banner (P6 Option A).

Phase 2 (2–4 days)
- P5 Option A: Integrate backup-security endpoint in UI analysis flow and render results.
- (Optional) P6 Option B: introduce minimal Monitoring rules; P7 expand rules for Backup/Monitoring categories.
- P8: Persist analysis with diagrams; expose re-analyze.

Phase 3 (ongoing)
- P9 transparency enhancements (link question text in vuln detail), P11 cache refinements, P12 documentation endpoints.

Acceptance Criteria
- API/DB conditional selections visibly change the questions asked (e.g., choosing GraphQL reveals GraphQL-specific questions) and produce enhanced vulnerabilities when risky options are selected.
- Completeness status is accurate for all node types and matches displayed total questions.
- Backup analysis produces vulnerability nodes on canvas when risky backup configurations are chosen.
- No false positives from client-side defaults; Unknown answers behave as expected in rules.
- Vulnerability details clearly state which selections triggered the rule, and users feel confident in traceability.

Risks &amp; Mitigations
- Increased questionnaire length with conditionals: Mitigate via progressive disclosure and breadcrumbs.
- Rules drift versus questionnaire changes: Address via introspection endpoints and mapping docs (P12).
- Performance: Use analysis caching but invalidate on answer changes; throttle bulk analysis.

Summary
These improvements align the questionnaire UX, data mapping, and rules engine to deliver accurate, explainable vulnerability results across WebApp, API, Database, Backup, and Monitoring. Enabling conditional flows and backup integration will immediately enhance relevance. Mapping fixes and removal of insecure defaults will increase trust. Persistence and transparency will improve repeatability and enterprise readiness.

WebApp Combined Questionnaire (Revamped Proposal v2)
Goal: Single, developer-friendly set that avoids naming vulnerabilities directly. Questions ask about real implementation choices. From answers, the platform infers likely risks (e.g., injection, XSS) and runs auto design review. 

Source merged: basic + advanced + expert (~56) → Proposed final: 18 questions (−68%)

Selection principles
- Use implementation language developers recognize (how do you do X?)
- No direct "Which vulnerability" or "How do you protect against X" phrasing
- Preserve dependency triggers: Database? API? → open child modals for those, not inside WebApp set
- Support robust scoring and rule mapping (each question emits security signals)

Proposed questions (ready to convert to YAML after your review)
Note: "Signals" are internal mappings we will use to infer risks/controls.

1) id: webapp_authentication_method
   type: single_choice
   question: How do users sign in to the application?
   options: ["OAuth2/OIDC (SSO)", "SAML SSO", "Username/Password with MFA", "Username/Password only", "No sign-in (public app)", "Unknown"]
   help_text: Authentication approach strongly influences account takeover risk.
   signals: { stronger: [MFA, SSO], weaker: [NoAuth, PWOnly] }

2) id: webapp_authorization_model
   type: single_choice
   question: How is access to features/data controlled after sign-in?
   options: ["RBAC with fine-grained permissions", "RBAC with basic roles", "Simple checks in code", "No authorization layer", "Unknown"]
   help_text: Fine-grained authorization limits blast radius of compromised accounts.
   signals: { stronger: [LeastPrivilege], weaker: [BroadAccess, MissingAuthZ] }

3) id: webapp_session_management
   type: single_choice
   question: How are user sessions handled?
   options: ["Secure sessions (HTTPOnly+Secure+SameSite; rotation; short TTL)", "Standard sessions", "JWT access+refresh with short TTLs", "Basic cookies only", "No sessions", "Unknown"]
   help_text: Session controls mitigate hijacking and fixation.
   signals: { stronger: [SessionHardening], weaker: [WeakCookies, LongTTL] }

4) id: webapp_https_enforcement
   type: single_choice
   question: How is transport security enforced for the app?
   options: ["HTTPS only + HSTS (redirect HTTP)", "HTTPS preferred", "Mixed HTTP/HTTPS", "HTTP only", "Unknown"]
   help_text: TLS and HSTS reduce MITM and downgrade risks.
   signals: { stronger: [TLS,HSTS], weaker: [MixedTransport, PlainHTTP] }

5) id: webapp_security_headers
   type: multiple_choice
   question: Which response headers are actively set by the app or platform?
   options: ["Content-Security-Policy (CSP)", "Strict-Transport-Security (HSTS)", "X-Frame-Options", "X-Content-Type-Options", "Referrer-Policy", "Permissions-Policy", "None/Unknown"]
   help_text: Security headers mitigate classes of web attacks.
   signals: { presence: [CSP,HSTS,XFO,XCTO,Referrer,Permissions] }

6) id: webapp_user_input_handling
   type: single_choice
   question: How are user inputs validated and normalized before processing?
   options: ["Centralized server-side validation (schemas, types, ranges)", "Basic server-side checks", "Client-side only", "Minimal/no validation", "Unknown"]
   help_text: Strong validation blocks malformed and dangerous inputs.
   signals: { stronger: [SchemaValidation], weaker: [ClientOnly, NoValidation] }

7) id: webapp_sql_statement_handling
   type: single_choice
   question: How are SQL statements built when accessing relational databases?
   options: ["ORM with prepared statements by default", "Parameterized queries", "String concatenation with manual sanitization", "Raw string concatenation", "No SQL used / Not applicable"]
   help_text: Parameterized/ORM approaches prevent unsafe query construction.
   signals: { stronger: [Parameterized], weaker: [StringConcat], risk: [InjectionRisk] }

8) id: webapp_nosql_query_building
   type: single_choice
   question: If NoSQL is used, how are filters/queries constructed?
   options: ["Whitelisted operators + server-side validation", "Validated JSON schema", "Free-form JSON from client with basic checks", "Free-form JSON from client without checks", "No NoSQL used / Not applicable"]
   help_text: Free-form filters without validation increase injection/abuse risk.
   signals: { stronger: [OperatorWhitelist, SchemaValidation], weaker: [FreeForm], risk: [NoSQLInjectionRisk] }

9) id: webapp_template_output_handling
   type: single_choice
   question: How is output rendered to the browser?
   options: ["Framework with auto-escaping (React/Angular/Vue templates)", "Server-side templates with auto-escaping (e.g., Jinja/EJS with escaping)", "Custom HTML string building with escaping", "Custom HTML string building without escaping", "Unknown"]
   help_text: Auto-escaping is critical to prevent script injection.
   signals: { stronger: [AutoEscape], weaker: [ManualHTML], risk: [XSSRisk] }

10) id: webapp_rich_text_processing
    type: single_choice
    question: Do users provide rich text/HTML content? If yes, how is it sanitized?
    options: ["Yes, sanitized with a well-known library (e.g., DOMPurify)", "Yes, basic allowlist stripping", "Yes, stored+rendered as-is", "No rich text content", "Unknown"]
    help_text: Sanitization of user HTML prevents stored DOM-based injection.
    signals: { stronger: [SanitizeLib], weaker: [AsIs], risk: [StoredXSSRisk] }

11) id: webapp_file_uploads
    type: single_choice
    question: How are user file uploads handled?
    options: ["Strict type/extension + size + antivirus scanning + isolated storage", "Type/size checks with isolated storage", "Basic type checks only", "Stored with minimal checks", "No file uploads", "Unknown"]
    help_text: Rigorous controls prevent malware and data exfiltration paths.
    signals: { stronger: [AVScan, IsolatedStorage], weaker: [MinimalChecks], risk: [MalwareUploadRisk] }

12) id: webapp_error_response_handling
    type: single_choice
    question: How are errors returned to users and logged?
    options: ["Generic user errors + detailed server logs", "Generic user errors, limited logs", "Detailed errors sent to users", "No structured handling", "Unknown"]
    help_text: Avoid leaking internals while maintaining audit trails.
    signals: { stronger: [NoInfoLeak, ServerLogs], weaker: [VerboseUserErrors] }

13) id: webapp_rate_limiting
    type: single_choice
    question: How is abuse/throttling handled for sensitive operations (login, search, forms, APIs)?
    options: ["Adaptive per-identity/IP/device", "Fixed per-identity/IP", "Global only", "No throttling", "Unknown"]
    help_text: Throttling limits brute force and resource exhaustion.
    signals: { stronger: [AdaptiveLimit], weaker: [NoRateLimit] }

14) id: webapp_third_party_scripts
    type: multiple_choice
    question: Which third-party front-end scripts/services are used?
    options: ["Tag managers (GTM/Tealium)", "Analytics (GA, Mixpanel)", "A/B testing", "Chat widgets", "Payments", "CDN-hosted libraries", "None/Unknown"]
    help_text: External scripts add supply-chain and DOM injection risk; CSP/Subresource Integrity can mitigate.
    signals: { presence: [ThirdPartyScripts], mitigation: [CSP,SRI] }

15) id: webapp_logging_monitoring
    type: single_choice
    question: What logging/monitoring exists for security-relevant events?
    options: ["Centralized security logging + alerting", "Application logs only", "Minimal logging", "No logging", "Unknown"]
    help_text: Monitoring supports detection and response.
    signals: { stronger: [SecMonitoring], weaker: [NoLogs] }

16) id: webapp_secrets_management
    type: single_choice
    question: How are application secrets (API keys, DB creds) managed?
    options: ["Dedicated secrets manager with rotation", "Environment variables in vault-managed runtime", "Config files with restricted access", "Hardcoded or repo-stored", "Unknown"]
    help_text: Proper storage prevents leakage and lateral movement.
    signals: { stronger: [SecretsManager], weaker: [Hardcoded], risk: [SecretLeakRisk] }

17) id: webapp_configuration_management
    type: single_choice
    question: How is configuration managed across environments?
    options: ["Immutable config + version control + change review", "Version-controlled config", "Manual edits on servers/containers", "Ad-hoc configuration", "Unknown"]
    help_text: Good config hygiene reduces misconfigurations.
    signals: { stronger: [ControlledConfig], weaker: [AdHoc], risk: [MisconfigRisk] }

18) id: webapp_dependencies_practices
    type: single_choice
    question: How are third-party dependencies managed?
    options: ["Automated scanning + pinning + updates", "Regular manual updates", "Occasional updates", "Rarely updated/unknown", "Unknown"]
    help_text: Dependency practices limit exposure to known CVEs and supply-chain attacks.
    signals: { stronger: [SBOM, Scanning], weaker: [StaleDeps], risk: [SupplyChainRisk] }
